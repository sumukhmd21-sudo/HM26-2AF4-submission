# Taste
- Centralize cross-cutting setup (e.g. `.env` loading) inside the module that consumes it, not at every entry-point script. This way every caller gets correct behavior by default and future scripts don't have to remember boilerplate. Confidence: 0.85
- When a runtime dependency (e.g. env var) is missing, throw a clear, actionable error message that names what to do (`"Copy .env.example to .env and fill it in"`), never silently fall back to a default like `localhost`. Confidence: 0.9
- When fixing a bug that involves a config value (env var, model name, feature flag), proactively audit **all related references** in the codebase — other env vars that may have the same problem, sibling files using the same pattern, stale comments referencing the broken value, and the `.env.example` / README docs. The user expects one pass to fix the whole surface area, not just the failing instance. Confidence: 0.9
- When editing a `.env` file that contains real credentials (API keys, DB URLs), **never overwrite the secret values** — only edit the specific lines you need to change. Read the file first, identify which lines contain secrets, and use targeted edits that leave every credential line byte-identical to what it was. Confidence: 0.95
- Before proposing a fix, read the files the user pointed to (don't assume — verify). The user often diagnoses root cause accurately and expects the assistant to confirm, not re-investigate from scratch. Confidence: 0.8
- Prefer idempotent seed/migration scripts (`ON CONFLICT DO NOTHING/UPDATE`, "re-run safely") so the user can run them repeatedly without manual cleanup. Confidence: 0.9
- Working on Windows with PowerShell. Default commands use PowerShell syntax (`copy`, `notepad`, `cd`), not bash. The project lives at `C:\Users\varun\my-website`. Confidence: 0.95
- For verification, user runs `type .env` (Windows) to inspect files — match this style when suggesting shell snippets. Confidence: 0.85
- When adding a new npm dependency, pin to an exact version (e.g. `"dotenv": "16.4.5"`), not a `^` range. Consistent with the rest of `package.json`. Confidence: 0.9
- Keep all imports at the top of the file in declaration order, even side-effect imports like `dotenv`. ESLint import/order rules matter. Confidence: 0.7
- When an SDK throws non-`Error` objects (e.g. `@google/genai` throws objects with `status`, `code`, `errorDetails` outside `Error.message`), always log the **full serialized object** — not just `(e as Error).message`. Use a helper like `serializeError` that pulls all own properties via `Object.getOwnPropertyNames`. Confidence: 0.95
- For API wrappers that can succeed at the HTTP level but return empty/garbage data (e.g. Gemini TTS returning a 200 with no `inlineData` because the model name doesn't support audio output), **never silently return `null`** — log the model identifier, `finishReason`, and a structural summary of what the response did contain. The whole point of returning `null` is "let the route show a nice error", but if you don't log *why* it's null, the next debugging session will be just as blind. A 503 with a server-side stack trace beats a 503 with a clean UI and a developer guessing. Confidence: 0.9
- When a route catches errors, distinguish failure modes by returning a typed error code (`CONFIG_ERROR` → 500, `AI_INVALID_OUTPUT` / transient API failure → 502) plus a structured `{ error, message, hint }` body — never a bare 502 with no diagnostic info. Include `durationMs` in error responses to help distinguish timeouts from instant failures. Confidence: 0.9
- When a domain error type exists (e.g. `GeminiError`), throw it instead of plain `Error` from low-level modules so upstream routes can branch on `.code`. Don't rely on string-matching error messages. Confidence: 0.9
- For Next.js API routes that call external APIs, always set `export const runtime = "nodejs"` and an explicit `export const maxDuration` — don't rely on defaults, which are too short for LLM calls. Confidence: 0.85
- After adding diagnostics, proactively supply a "what to check next" table mapping likely error codes (404, 429, PERMISSION_DENIED, ENOTFOUND, etc.) to concrete fixes. The user wants actionable next steps, not just logs to grep. Confidence: 0.85
- When fixing one route's error handling, proactively apply the same pattern to sibling routes (e.g. `analyze-image`, `voice/transcribe`) that share the same external dependency — assume they have the same bug latent in them. Confidence: 0.8
- For parsing LLM/AI responses, use a **lenient parser with multiple fallbacks** (direct parse → strip ```json fences → extract first {...}/[...] block → throw with raw preview). Never assume AI output is clean — always handle markdown fences and surrounding prose. Confidence: 0.9
- For external API calls with model/feature compatibility quirks (e.g. Gemini transcribe models rejecting `systemInstruction` or `responseMimeType: "application/json"`), build **resilient wrappers that retry without the rejected feature** rather than hardcoding per-model branches. Pre-disable flags should exist so callers can skip bad features up front, but the wrapper should also auto-detect and retry as a safety net. Confidence: 0.85
- For LLM structured-output calls, prefer the SDK's native `responseSchema` (JSON Schema alongside `responseMimeType: "application/json"`) over prompt-template JSON examples + lenient text parsing. Schema-constrained output eliminates the whole class of bugs: truncated JSON, invented field names, malformed escapes, markdown fences. Keep the local Zod schema as the server-side source of truth, and keep the lenient parser only as a fallback for non-schema calls. Confidence: 0.95
- When the spec says "model name from env var" but the configured model can be invalid/missing/fictional, **honor the spec contract AND add a silent fallback chain** of known-working models rather than failing hard. If the primary returns empty/empty-text or a model-not-found error, try the next candidate and log the failure of the previous one. The env var stays the primary config; the chain is a safety net for real-world invalid configs. Confidence: 0.9
- When a feature is gated by an env var that could point to an invalid model, surface a clear "what to change in `.env`" recommendation alongside any fix — name the fictional/current-broken model, name a known-working replacement, and offer both "set env to working model" and "leave env, let fallback handle it" options. Confidence: 0.85
- When targeting Gemini's `responseSchema`, use **OpenAPI 3.0 subset syntax** — single-string `type` only, nullable fields expressed as `{ type: "string", nullable: true }`. Gemini rejects JSON Schema union syntax (`type: ["string", "null"]`) with "Proto field is not repeating, cannot start list". Also avoid `$ref`, `anyOf`/`oneOf`/`allOf`, `additionalProperties: false`, `type: "null"` alone, `const`, `examples`, `default`, `format`. Allowed: `type`, `nullable`, `enum`, `properties`+`required`, `items`, `description`, basic numeric/string bounds. Confidence: 0.95
- For Gemini `responseSchema` objects, **hand-write the schema as a literal object** instead of auto-converting from Zod or any schema library. Gemini's accepted subset is small enough that a hand-written literal is clearer in code review, can't drift through an auto-converter, and forces the dev to confront the constraints directly. Keep Zod as the server-side runtime validator only. Confidence: 0.9
- When using `edit_file`, the `old_string` must cover a **literal exact-byte match** and the `new_string` must contain **every symbol** the post-edit file should still expose. If an earlier edit swapped a multi-constant header for just a comment block, restore the missing constants (re-verify with a `grep` for each identifier used downstream) before trusting the fix. After any edit that touches a file's top-of-file declarations, immediately grep for every function/constant referenced later in that file — caught-one-missed-the-other bugs are silent until runtime. Confidence: 0.95
- When fixing a non-trivial bug, **don't guess the symptom** — explore the codebase first to find all relevant call sites and root causes, then use `ask_user_question` to confirm which symptom the user is actually seeing and what scope of action they want (diagnose-only vs diagnose-and-fix vs UX-improvement). Multiple-choice with concrete options beats open-ended "what do you want?" The user appreciates being asked to disambiguate before code is written. Confidence: 0.9
- For non-trivial multi-step fixes, use `todo_write` with a numbered, status-tracked list (in_progress → completed). Update the list at meaningful checkpoints, not after every keystroke. The user uses this as a progress indicator and to verify nothing was skipped. Confidence: 0.9
- After typecheck/build surfaces errors, **distinguish new errors from pre-existing ones** by stashing your changes and re-running against the baseline (e.g. `git stash && tsc ... && git stash pop`). Only report the errors your changes introduced — don't claim pre-existing unrelated errors as part of the fix. This is baseline hygiene the user expects. Confidence: 0.95
- **Catch your own mistakes mid-fix and self-correct immediately.** If you notice a follow-on edit is wrong (e.g. a button dispatches a stub that breaks the next step), revert/adjust in the same turn rather than waiting to be called out. The user values iteration speed and clean final state over appearing correct on the first attempt. Confidence: 0.9
- Prefer **typed unions over freeform `string` enums** for domain reason codes (e.g. `LocationReason = "INVALID_COORDINATES" | "LOW_ACCURACY" | ...`). A `string` reason field is an open door to silent typos and unhandled values; a union forces exhaustive switches in the UI and makes missing branches a compile error. Include both server-emitted reasons AND client-only ones (like `LOCATION_PERMISSION_DENIED`) in the same union so the callback signature stays type-safe end-to-end. Confidence: 0.95
- When multiple signals could decide a domain fact (e.g. polygon containment vs reverse-geocoder state), **pick the authoritative one as source of truth** and treat the others as enrichment only. If the enricher fails, return success with a separate warning reason — never fail the primary check because an enrichment step hiccupped. Confidence: 0.85
- Map browser/platform error codes (`GeolocationPositionError.PERMISSION_DENIED`, `POSITION_UNAVAILABLE`, etc.) to your **own typed reason codes** in the boundary layer, not at the UI site. The boundary file is the one place that knows the platform API surface; everything downstream should speak your domain types. Confidence: 0.9
- Never ship UX copy that contradicts the actual state (e.g. "Please allow location access" spoken by voice when location was already collected and validated). If a prompt is misleading, delete it rather than rewrite — misleading copy is worse than no copy because the user trusts it less going forward. Confidence: 0.85
- When fixing a bug, look beyond the literal symptom to **all callers and side effects of the broken logic**. A bug in one validation step can manifest as wrong copy in a completely different screen. Trace the data flow end-to-end before editing. Confidence: 0.9
- When an initial fix doesn't resolve the user's reported symptom, **don't iterate on the same surface-level fix** — go back, look for a deeper root cause. The user reports the literal UI text they saw; what's broken is often two layers down (e.g. an inverted tuple convention in a helper, or a config var polluting the test env). Re-investigate end-to-end before tweaking the same code again. Confidence: 0.9
- When debugging needs runtime verification of a helper's behavior, write a **throwaway diagnostic script** in `scripts/` (e.g. `scripts/diag-poly.mjs`) that inlines or imports the suspect function and prints results for known inputs. Delete it with `Remove-Item scripts/diag-*.mjs` after the diagnosis — these are not meant to live in the repo. Confidence: 0.85
- For unit tests that exercise code which calls external HTTP services (geocoder, AI APIs, payment providers), **mock the external module with `vi.mock("@/lib/.../external", () => ({ fn: async () => ({...}) }))`** at the top of the test file. Tests must not hit the network — flaky third-party responses produce flaky CI. Keep the mock realistic (state, district, city) so enrichment paths are exercised. Confidence: 0.9
- When changing a configurable value (env var, magic number, threshold), update **both `.env` and `.env.example` together** so local dev and fresh-clone setups stay in sync. Add an explanatory comment above the line describing the trade-off (e.g. why 2000 m and not 50 m — desktop browsers, indoor phones, polygon-as-real-guard). If the bug was caused by an invalid enum/identifier value (wrong model name, wrong region code, wrong tier), the comment should also **list the full set of valid values** so the same trap can't be re-set from a fresh clone. Confidence: 0.9
- When the same value is consumed from multiple places (env var, shell `$env:`, `.env` file), suspect **stale shell environment** as the source of confusing test failures. Run `Remove-Item Env:VAR -ErrorAction SilentlyContinue` before each test run and verify with `node -e "console.log(process.env.VAR)"`. Stale shell vars will silently override file changes and look like code bugs. Confidence: 0.85
- For data structures with a coordinate convention (polygons, bounding boxes, geo coordinates), **fix the helper to match the storage convention rather than rewriting all callers**. If polygons are stored `[lng, lat]` (Leaflet, maps) but the point-in-polygon helper expects `[lat, lng]`, fix the helper's tuple destructuring — don't refactor every call site. Add a comment explaining the convention so future readers don't flip it back. Confidence: 0.9
- When running vitest from PowerShell, the output is noisy — use `Select-String -Pattern 'Test Files|Tests|FAIL|✓ |× '` to surface the summary, or `'AssertionError|Expected|Received'` for failure details. Don't pipe through `tail`/`head`; PowerShell uses `Select-Object -First N -Last N`. Confidence: 0.85
- The user reports bugs as the literal UI text they see ("it still says X"). Don't assume their interpretation of root cause is right — they only see the symptom. The actual bug is often orthogonal to the reported copy (e.g. polygon convention mismatch surfacing as "Couldn't accurately verify your location"). Trust the symptom text, distrust the implied diagnosis. Confidence: 0.85
- For citizen-facing complaint flows (low-literacy / low-tech-comfort users), prefer **voice-first, guided-conversation UI**: a named, stateful agent (e.g. "Rammana") that greets the user in the local language, asks one question at a time, and walks them through each step (greet → describe → location → photo → return tracking ID). Don't dump a complex multi-step form. The agent should expose a mute toggle and a "skip voice — type instead" fallback for accessibility. Confidence: 0.95
- For voice-driven complaint intake, **a short transcript (2–3 words) is acceptable as the user's contribution** — the LLM enrichment step (image analysis + voice transcript → proper description) is what fills in the details. Don't force the user to dictate a full sentence; friction kills adoption. The voice transcript flows into the AI description generator alongside the photo so the LLM has both signals. Confidence: 0.9
- For local-language voice assistants, ship **bilingual UI presentation**: every utterance renders in the local script (e.g. Kannada) with a small transliterated/translated English gloss underneath for accessibility. The tracking ID should be shown in both scripts (with local numerals — ೦–೯ for Kannada) and spoken aloud in the local language on the success screen, with a Replay button. Confidence: 0.9
- When the user proposes a flow order, **surface tradeoffs before coding** — e.g. "voice before camera means the LLM has no image to enrich with" vs "voice after camera enables richer AI descriptions". Use `ask_user_question` with concrete multiple-choice answers so the user can pick the trade-off they want, rather than silently choosing for them. This applies even when the model thinks it has a clear "recommended" option. Confidence: 0.85
- For TTS in non-English scripts via Gemini, the prebuilt voices (Kore, Aoede, etc.) are multilingual — pick a non-Latin-friendly persona (e.g. "Aoede" for Kannada) and pass the script text directly. Document the caveat that prosody may sound off and offer a swap path to a dedicated TTS provider (e.g. Google Cloud TTS `kn-IN`) if quality isn't acceptable. Keep the TTS route's input contract (`{text, voice?, language?}`) stable so consumers don't need to change when the backend swaps. Confidence: 0.85
- On **Windows + Next.js + dotenv**, already-set environment variables (system/user level, or exported in the shell) take precedence over `.env` file values — dotenv does NOT override existing `process.env` entries by default. When a config change in `.env` doesn't take effect, suspect stale shell/system env first. Verify with `echo %VAR_NAME%` (cmd) or `$env:VAR_NAME` (PowerShell). Don't waste cycles re-reading the .env file — the runtime is reading it correctly; the system env is just winning. Document this gotcha next to any "set this in .env" instruction. Confidence: 0.9
- For defensive config that can be silently broken (wrong model names, deprecated API versions, fictional identifiers), build a **known-bad blacklist with silent fallback** at the consumer site (e.g. `MODELS.tts()` checks `process.env.GEMINI_TTS_MODEL` against `BAD_TTS_MODEL_NAMES`, falls back to a working default and `console.warn`s). This protects against shell-env pollution, stale `.env` files, typos in fresh clones, and copy-pasted config from outdated docs — all without requiring the user to clean up their environment. Bad env config becomes a warning, not a hard failure. Confidence: 0.9
- When debugging silent server-side failures (503s, empty responses, "works on my machine"), add **temporary diagnostic fields to the route's error response** (e.g. `{ error, synthesizeError, debug: { model, keyPrefix } }`) and remove them after the bug is found. This bypasses the problem of background-server stdout not being captured/visible to the assistant (npm scripts that swallow output, Windows cmd vs PowerShell differences, `tee` not existing on Windows). The HTTP response is always visible — put the diagnostic info there. Confidence: 0.9
- For voice-driven features, **audio must actually play out loud** — displaying the utterance as text is not an acceptable substitute. The user explicitly rejected a "text-only greeting" implementation as broken. If browser autoplay policy blocks playback, the fix is to gate the first utterance behind a user gesture (e.g. "Press to begin" button) plus AudioContext.resume() and a primed silent <audio> element, NOT to silently fall back to text. Always verify TTS end-to-end (fetch → audio.play() → onended) and surface failures visibly with a diagnostic banner so silent regressions don't ship. Confidence: 0.95
- When adding retry logic around external API calls, **scope retries to specific transient failure modes only** — not to all failures. E.g. "retry only when the API returns a 200 with empty data (finishReason=OTHER, parts=undefined)" OR a thrown SDK error (ClientError/ServerError from a transient HTTP failure) — NOT on rate limits, quota exhaustion, CONFIG_ERROR, or PERMISSION_DENIED, which retrying would make worse. If the wrapper conflates multiple failure modes into one return value, refactor it to throw a **typed error** (e.g. `TtsError` with `kind: "RATE_LIMITED" | "QUOTA_EXHAUSTED" | "CLIENT_ERROR" | "SERVER_ERROR" | "NO_AUDIO"`) so callers can branch on `.kind` rather than string-matching messages. The user prefers 3 attempts max with **exponential backoff** (500ms, then 1000ms, then 2000ms between attempts) for transient cases, and only the final failure becomes a user-visible error. Confidence: 0.95
- For browser audio playback, **never attempt `audio.play()` or `AudioContext.resume()` before a user gesture** — every browser blocks it. Gate the first playback behind an explicit user action (a "Press to begin" tap, mic button press, etc.) and track this with a `useRef` flag (`interactedRef`) checked at the call site. Don't use `useEffect` to auto-play on mount, and don't silently retry blocked playback — just don't try. Confidence: 0.95
- For idempotent UI side effects (appending chat messages, enqueueing notifications, logging analytics), **dedupe by content identity** (`${key}|${text}`) using a `useRef<Set<string>>` checked before mutating state. This prevents retry/replay paths from producing duplicate bubbles — the user explicitly named "same greeting bubble appearing duplicated multiple times in the chat" as a bug to fix. The check belongs at the mutation site, not deeper in the network/transport layer, because the same content can be appended via different code paths. Confidence: 0.9
- When the user's bug report describes both a backend symptom and a frontend symptom in the same message, **fix both as part of one pass** even though they're in different files. The user expects one bug report → one coherent fix covering the full data flow, not "fixed the server, frontend is your problem". Cross-cutting fixes (route handler + consuming component) belong in the same edit cycle. Confidence: 0.9
- The user thinks about bugs in terms of **specific failure-mode semantics** rather than generic error handling. When reporting or fixing bugs, name the exact failure mode ("no audio data" vs "thrown exception", "browser autoplay block" vs "API 503", "duplicate append" vs "double network request") and treat each one as a distinct case with its own fix. Generic "try/catch and retry" answers miss the point. Confidence: 0.85
- For API routes that talk to a database, **wrap the DB query in a try/catch and return a clean JSON error response** (`{ error: "INTERNAL_ERROR" }` with status 500) instead of letting a thrown DB exception crash the route with no body. Log the underlying error to the server console so missing-column / connection issues aren't hidden. A raw stack trace or empty 500 makes the bug undiagnosable from the client. Confidence: 0.95
- **Non-critical side effects (audit logging, analytics, telemetry) must never block a successful primary operation.** Wrap them in their own try/catch with a `console.error` so a logging failure can't break login, write, etc. The user wants the happy path to succeed even if the side effect channel is down. Confidence: 0.9
- For verifying a fixed API route end-to-end, **start the dev server and hit the endpoint with curl** — don't rely solely on typecheck + unit tests. Typecheck proves the code compiles; tests prove the unit logic; a real HTTP request proves the route actually returns the expected JSON + status code under realistic conditions. Check success AND failure paths (valid input, invalid input, missing resource) to confirm all branches return clean responses. Confidence: 0.9
